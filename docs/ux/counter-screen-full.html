    How this was built

    UX and QA, working the same list

    Each region below got the same question twice: what does the operator need here, and what happens when someone does the wrong thing here. Where the two pulled against each other, that tension is written down rather than quietly resolved in the code.

    The bug you found

    What happened — the switcher opened with a header and nothing under it; the short-basket panel was visible before anyone pressed "Log short basket." Both use hidden to stay closed, and both have a class rule setting display: flex. Browsers apply origin before specificity — an author stylesheet rule beats the browser's built-in [hidden]{display:none} regardless of whose selector is more specific, so the moment either element got a display value in CSS, the hidden attribute stopped doing anything. It looked like a data problem; it was a visibility problem hiding a real one underneath — the switcher genuinely was empty, because it's only ever populated inside the same click handler that reveals it, and that handler had never run.

    Fix — one rule, [hidden]{display:none!important}, added once near the top of the stylesheet, ahead of every component rule, so no future overlay can reintroduce this by picking `display:flex` for its own layout. Also patched the same latent bug in counter-variant-simulator.html's short-basket panel, which had it too but hadn't been clicked into yet.

    Zero & tare, before every pile

    UX — FR‑3 only required this once, at sale start. Doing it again before each pile — nothing on the scale reads zero, then the empty bucket gets its own weighed reading — costs a few seconds and buys the same thing the public count buys: nobody has to take the number on faith, because they watched it get measured for this pile, not assumed from the first one. Default on, for every user; the settings panel (gear icon, top right) is where a tenant relaxes it to once-per-sale.

    QA — "Not zero" must never block — it flags (a system log entry, same non-blocking pattern as the clock anomaly) and still lets the operator continue to the tare step. Turn the setting off mid-sale and check the *next* new pile skips straight to step 3 — but the pile already mid-count when you flipped the setting must be unaffected, since its own check already happened or is already running.

    Weight entry — drag, nudge, or type

    UX — Plus-and-minus alone doesn't scale — going from 2 kg to 43 kg one click at a time is exactly the kind of friction that gets a feature ignored in the field. Now there are three ways into the same value: a native range slider for a fast coarse drag, ± buttons stepping 0.5 kg for a fine nudge, and a plain text field for typing an exact number directly. They all write to the same value live, so nobody has to pick a "mode."

    QA — Typed values aren't forced to the 0.5 kg step — 43.3 is a legitimate scale reading and rounding it would misreport real money. All three inputs are clamped to sane physical bounds (a bucket isn't 40 kg; a short basket can't read under its own tare) so a mistyped digit can't silently corrupt a total. "Default to last use" is implemented honestly at session scope only — the field that matches whichever input you used most recently gets focus on the next entry; nothing is written to storage, and the settings panel says so rather than implying a persistence that isn't there yet.

    Every log line shows its own arithmetic

    UX — A bare "counted" told you nothing you could check. Every standard-basket row now carries its own derivation — tare + standard net = expected reading — and every short basket shows the actual triple: scale reading, tare, and the net that's left once you subtract it. Closing a pile shows the same split at pile scale. This is FR‑7.4's "no single opaque total" applied down to the finest-grained row in the record, not just the settlement screen.

    QA — The short-basket number was previously ambiguous — was it a net figure or a scale reading? It's now explicitly the gross reading (matching FR‑5.6 exactly: "recorded with its actual scale reading, and the app derives its net weight from the tare"), with net computed and shown live as you adjust it, before you ever confirm. Check the math by hand against a couple of entries — reading minus this pile's own tare, not a stale one from a previous pile.

    New findings from this round

    • F-21

      Zero and tare checking, repeated before every pile rather than once per sale, generalises what Open question 4 in the original findings only asked about hypothetically (different basket types mid-sale). Made configurable rather than fixed, since the right default for a two-person sale and a large crew sale may differ — defaulting on, letting it relax per tenant.

    • F-22

      Stepper-only weight entry (±1 kg per tap) doesn't scale to real bucket and rubber weights. A drag-slider, a coarser ±0.5 kg nudge, and direct typing now coexist on the same value rather than forcing a mode choice — and surfaced a correctness gap in the short-basket flow: it was logging a bare number where FR‑5.6 specifies a scale reading with the net derived from tare, now fixed.
